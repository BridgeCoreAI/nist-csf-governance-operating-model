# Assessment Method

## Core Principles

1. Each control is assessed independently. Findings and recommendations are not reused across controls unless the evidence clearly supports doing so.
2. The exact control description and control-specific assessment questions are used for every assessment; no generic substitute questions.
3. Control status is determined before maturity is assigned. These are separate judgments.

## Control Status Values

- **Pass**: the control is designed appropriately and operating effectively, supported by evidence
- **Partial Pass**: the control is designed appropriately but operating effectiveness is incomplete or inconsistently evidenced
- **Fail**: the control is not designed appropriately, not operating, or evidence contradicts the claimed state
- **Not Assessed**: insufficient information exists to reach a determination

## Design Assessment vs. Operating-Effectiveness Assessment

Design assessment asks: is the control, as specified, capable of achieving its intent if followed correctly?
Operating-effectiveness assessment asks: is the control actually being followed, consistently, with evidence?
A control can pass design assessment and still fail operating-effectiveness assessment. Both are recorded separately in every control record.

## Evidence Standard

Every finding must be supported by specific evidence: concrete facts, metrics, dates, approvals, decisions, records, or documented activities. Evidence limitations are stated explicitly rather than implied. GitHub activity may support evidence traceability but does not by itself prove control effectiveness.

## Recommendation Standard

Every recommendation addresses the exact gap identified in its paired finding. Recommendations do not introduce unrelated requirements and are not generic. Automation is recommended only when it is relevant to the specific control, process, evidence gap, or maturity gap identified, not by default.
